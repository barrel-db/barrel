# Implementation prompt for Barrel design templates and views

Work in the Barrel repository. Design and implement `barrel_design`, an optional OTP application for versioned database designs with automatically maintained, queryable views. A design author can declare a native projection, write a CouchDB-style map in WAT, or compile Zig to portable Wasm. Borrow named templates, categorized columns and drill-down from Lotus Notes. An application should be able to install a receivables design, record a payment and read the updated customer subtotal with a bounded wait.

## Start from the evidence

1. Read the architecture note and inspect the current Barrel and `erlang_wasm` sources before choosing integration points. Verify the pinned dependencies and supported OTP versions. The existing invoice example uses real Barrel databases and a process-local checkpoint. The optional public API, durable index and generation switching are implementation work. [Architecture and database survey](wasm-views.md) · [Runtime and build paths](wasm-views.md#from-wat-or-source-code-to-a-reusable-module) · [Runnable invoice example](examples/receivables/README.md)
2. Produce a short, source-linked implementation plan. Check current database uses of Wasm against primary documentation. Identify which patterns Barrel should adopt for module publication, compile reuse, capabilities, limits and materialized indexes. Explain the benefits and costs of background, synchronous, lazy and manual indexing. Recommend the v1 scope and list the changes each Barrel application needs. Evaluate Notes-style forms, folders and agents, BQL scalar functions and export transforms as possible later extensions. [Notes design concepts](wasm-views.md#lotus-notes-design-templates-and-categorized-views) · [Indexing trade-offs](wasm-views.md#when-to-update-a-view) · [Extension candidates](wasm-views.md#other-end-user-extensions)

## Implement the first usable release

- Install a named, versioned design per database through `barrel_design:install(Db, Design, Modules)`. Persist the manifest and portable module bytes by digest. Verify their correspondence, ABI, exports, allowed imports and resource limits before activation. Make repeated installs of the same version idempotent. Keep optional dependencies out of the default Barrel profile. Give the optional profile a build and test job on its supported OTP release.
- Accept inline WAT for preview and a reproducible path from WAT or Zig source to a deployable `.wasm` artifact. Load and prepare each distinct binary once per node while in use. Keep a supervised holder across calls, drain users before unloading and restore from portable bytes on restart. Start with `barrel_v1.field` for declared typed fields and `barrel_v1.emit` for bounded key/value pairs. Document missing fields, signed amounts, invalid output and traps. [WAT example and ABI](wasm-views.md#a-view-a-developer-could-publish) · [Zig source](examples/receivables/open_by_customer.zig) · [Guest binding](examples/receivables/invoice.zig)
- Run every untrusted map with fresh guest state, finite fuel, a host-enforced wall-clock deadline, and explicit limits on guest pages, stack depth, host calls, input and emitted bytes/rows. Bound host process memory, queues and concurrent workers per database and node. Stage emissions until the call succeeds. Run outside the source write transaction with only the declared imports. Demonstrate that termination releases resources and leaves the last published index readable. In `erlang_wasm` 0.11.2, finite-fuel calls reuse a prepared module and execute in the interpreter. If proposing generated BEAM code, demonstrate actual compiled entries and measure the eligible configuration separately with its exact limits. [Runtime isolation and limits](wasm-views.md#execution-and-memory-limits)
- On installation, schedule an automatic backfill from a consistent source snapshot and its watermark, then follow the durable document feed even with zero readers. Cover direct, bulk and replicated changes, winner changes, deletes and expiry. Serialize index publication per database instance, view and generation. Atomically replace a source document’s old emissions, reverse entries and durable checkpoint. Preserve repeated keys with a stable emission ordinal. Specify key collation, snapshot pagination, and how encrypted databases protect derived rows. Rebuild into a new generation on an incompatible design change, history gap or changed source identity. Keep the last complete generation available during a rebuild. [Index and recovery design](wasm-views.md#maintaining-and-querying-the-index)
- Support ordered key and range reads, category prefixes, limits, continuations, native `_count` and exact integer `_sum`. Return the published generation and indexed-through checkpoint with a query. Default reads return immediately from a complete generation and report `building` during the first build. Restrict view and aggregate access to principals authorized for the indexed input.
- Implement `barrel_design:refresh(Db, View)` and `refresh/3` with `#{timeout_ms => N}` and a 1,000 ms default. Capture one source instance and sequence when accepting a refresh, wake the existing worker, and coalesce concurrent requests. Return `{ok, Checkpoint}` once that target is covered. An up-to-date refresh should invoke zero guest maps. A query with `freshness => {wait_for, Target}` observes progress to its fixed target. On timeout return an error with the reached checkpoint while indexing continues. Keep a full rebuild as a separate administrative operation. [Freshness and refresh contracts](wasm-views.md#when-to-update-a-view)

## Deliver an executable example and correctness tests

Build the receivables guest from Zig and install it through the new public API. The selector picks open invoices. The map emits `([customer, due_on], sum(line_cents))`. Show the original documents, manifest, build command, ordered rows and grouped subtotal. Include the equivalent native projection and a minimal WAT example. Show both the immediate read and the read that waits for a source write.

Use `View = {<<"receivables">>, <<"open_by_customer">>}`. Drill into Ada’s rows with `barrel_design:query(Db, View, #{key_prefix => [<<"Ada">>], reduce => false})`. Initially return `inv-102` at 1,800 cents then `inv-101` at 750 cents, for a subtotal of 2,550. Mark `inv-102` paid and wait for its write checkpoint. Ada’s subtotal must be 750. Import a 500-cent open invoice, call `barrel_design:refresh(Db, View)`, then read with `reduce => true, group_level => 1`. The subtotal must be 1,250. Bea’s subtotal stays 900. Verify that the reads execute zero guest maps. [Complete fixture, queries and output](examples/receivables/README.md#query-the-same-design-through-the-proposed-api)

Exercise indexing with no readers, repeated emissions, keys moving between categories, TTL, concurrent writes during backfill, crash and replay at publication boundaries, same-name database recreation and a definition upgrade with readers in flight. Compare each recovered index to a clean recomputation. Test that concurrent refreshes share work, a later write cannot move an accepted target, and one caller timing out leaves other waiters and indexing running. Test fresh guest state, fuel exhaustion, elapsed deadline, page and output limits, partial-emission rollback and worker cleanup. Report the commands, observed outcomes and any unsupported cases. [Acceptance criteria](wasm-views.md#delivery-plan-and-acceptance-criteria)

## Measure the implementation and publish the evidence

Run both example targets from the repository root to establish the prototype baseline on the test machine.

```sh
make -C docs/architecture/examples/receivables run
make -C docs/architecture/examples/receivables bench
```

The 27 November 2026 prototype run on an Apple M4 Pro backfilled 3,076–4,456 source invoices/s with the finite-fuel Zig map and 6,365–7,421/s with the native map. Each Wasm run loaded the module once for 1,600 matching invoices. Reads and already-current refreshes added zero guest calls. Use these three-trial ranges as a reference when reproducing the workload. [Prototype measurement and methodology](wasm-views.md#measured-invoice-indexing-performance) · [Per-trial data](examples/receivables/benchmark-2026-11-27.csv) · [Benchmark source](examples/receivables/receivables_bench.erl)

Benchmark the **new public install, write, refresh and query paths** alongside that baseline. Run with views disabled, with an equivalent native Erlang projection, and with the finite-fuel Zig/Wasm map. Keep the data, durability settings and applicable queries the same. Validate rows and subtotals before interpreting a timing.

| Question | Evidence to collect |
|---|---|
| Can code be reused across isolated calls? | Time build/translation, first module load, cold install to first queryable generation and warm invocation separately. Count actual module loads, guest calls and any generated-code entries. Repeat reads and an already-current refresh and show the observed count deltas. |
| Can the index keep up? | Measure backfill in source documents and emitted rows per second, sustained incremental throughput and lag to a fixed checkpoint. Exercise a mixed write stream and a burst with concurrent readers. Time an explicit refresh of a backlog separately from an already-current refresh. Report backlog size and poll/batch settings. |
| What do foreground callers pay? | Report p50/p95/p99 write and view-read latency, sample counts and workload concurrency. Run multiple independent trials with the mode order rotated. Include small projections, fan-out and a realistic guest. Test interference between tenants. |
| Do the limits and recovery hold? | Measure peak node RSS, guest pages, index bytes relative to source bytes, actual time to terminate, and recovery time after interruption. Correlate limit failures with discarded emissions, resource release and a valid checkpoint. |

Record the date, commit and working-tree changes, host/OS, OTP/ERTS, engine and compiler versions, guest digest, scheduler count, dataset, resource limits, timing boundaries, cache state, warm-up, trial order and exact commands. Publish per-trial data with units and keep the harness in the repository. Put the findings and their scope in `docs/architecture/wasm-views.md`. Link the measurements to the harness, data and correctness tests, link this prompt from the design, and verify every new relative link and heading anchor. Mark anything unmeasured as pending. Base a deployment recommendation on measured headroom against its stated write rate, latency objectives and memory budget. Where those objectives are unknown, report the measured envelope and the open decision.
